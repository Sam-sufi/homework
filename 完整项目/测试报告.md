## 1 测试目标与范围

### 1.1 目标

1. 用**单元测试**逐个验证关键函数自身的规则，把"价格换算、密码散列、时间窗口、审计脱敏、通知队列"这类容易回归的逻辑固定下来；
2. 用**集成测试**从 HTTP 入口验证真实链路（请求 → 鉴权 → 业务 → 数据库 → 响应），覆盖并发、越权、事务回滚、导出等只能在整链路上观察的行为；
3. 给出可复核的证据：命令、环境、原始输出、覆盖率与未覆盖说明。

## 2 测试策略

### 2.1 单元测试与集成测试的分工

| 维度 | 单元测试 `tests/test_unit.py` | 集成测试 `tests/test_app.py` |
| --- | --- | --- |
| 被测对象 | 单个函数（含私有工具函数） | HTTP 接口 + 业务 + 数据库整链路 |
| 隔离方式 | 直接传参，不经 HTTP、不经 `act()` | 真实 `ThreadingHTTPServer` + 真实 HTTP 请求 |
| 数据库 | 临时库：模块启动建一次演示库，每个用例复制一份 | 临时库 + 随机端口（`port=0`），用例间完全隔离 |
| 失败定位 | 直接指向函数与断言 | 定位到接口与状态码，需要看数据库副作用 |
| 数量 / 耗时 | 78 项 / 2.7 秒 | 27 项 / 66.3 秒 |
| 主要价值 | 规则边界、异常分支、时间窗口 | 鉴权、CSRF、并发、事务、响应与导出 |

两类测试互补：单元测试把"函数级规则"钉死，集成测试保证"这些函数装配起来仍然正确"。

### 2.2 可重复性措施

1. **不碰日常数据**：单元测试用 `tempfile` 建库后复制模板；集成测试每个用例新建临时库，`tearDown` 关服务、停线程、删目录。整个测试过程 `data/campus.db` 大小与内容不变。
2. **不依赖网络与第三方服务**：服务绑定 `127.0.0.1` 与随机端口，无需外网。
3. **不 sleep 等时间**：72 小时交付窗口、2 小时撤回窗口的用例直接改数据库里的时间戳（`now() - 7201`、`now() + 73*3600`），结果稳定且秒级完成。
4. **时间断言留余量**：接单时间用"当前 +1 小时"，避开整分/整秒边界。
5. **并发用例可复现**：两个买家抢同一商品依赖 `BEGIN IMMEDIATE` 与部分唯一索引，断言"恰好一单成功"；同一买家重复下单断言"一单成功 + 其余返回订单已存在"。

### 3.2 关键函数的测试要点

#### 3.2.1 密码散列 `core.password_hash` / `core.valid_password`

- **为什么单测**：这是"库里不能出现明文密码"的唯一边界，且校验用了恒定时间比较，写错不会在功能上暴露。
- **怎么测**：断言返回值为 `盐:散列`（32 位盐 + 64 位 SHA-256）；同一密码两次散列不同（盐随机）；错误密码、少一位、大小写不同均返回 `False`；传入固定盐时结果可复现，说明实现是确定性的；中文密码可往返。

#### 3.2.2 字段校验 `core.text` / `core.boolean`

- **为什么单测**：`text` 被 20 多处调用，它的类型判断顺序（先查类型、再去空白、再查长度）决定了错误提示是否准确。
- **怎么测**：`None`、数字、列表、字典、布尔都抛 `BusinessError`；`'  高等数学  '` 返回去空白后的值；`'  短  '` 因去空白后仅 1 字被拒，证明长度按去空白后计算；长度上下界本身可接受（`2` 与 `50` 都通过）。
- `boolean` 只接受 JSON `true`/`false`，字符串 `"true"`、数字 `1` 一律拒绝——这对应"质量问题修正记录"里 Q03 的回归点。

#### 3.2.3 商品字段与图片 `services._product_fields`

- **为什么单测**：发布与编辑共用它，历史缺陷（Q02：字符串 `Infinity` 导致 500）就出在金额换算上。
- **怎么测**：`'12.50'`、`35`、`'0.01'`、`1000000` 分别得到 `1250`、`3500`、`1`、`100000000` 分；`'Infinity'`、`'-Infinity'`、`'NaN'`、`'abc'`、`None`、`[]`、`{}` 统一抛"价格必须为有限数字"而不是溢出；`0`、`-1`、`1000000.01`、`1e12` 超范围被拒。
- 图片做了三层校验：前缀必须是 PNG/JPEG 的 data URL、Base64 必须能严格解码、解码后的文件头必须是 PNG/JPEG 魔数；另加 5MB 上限（用真实 5MB+ 载荷验证）。

#### 3.2.4 统一入口 `services.act`

- **为什么单测**：所有写操作的封禁拦截、分发、审计都在这里，它的分支最容易被新动作破坏。
- **怎么测**：未知动作抛"未知操作"；被封禁用户 `order` 被拒，但 `read_notices` 仍可执行（兑现"封禁不打断在途履约"）；同一买家重复下单走 `EarlyReturn` 分支时**不写审计**（审计条数仍为 1）；审计的 `detail` 中不含 `image` 与 `password`、超长内容截断到 2000 字；`target` 取 `payload['id']`、`created` 有值。

#### 3.2.5 交易状态机与时间窗口

- **怎么测**：接单时间用"过去 1 小时""73 小时后""错误格式"三种输入分别断言同一条提示；撤回窗口把 `buyer_confirm` 改成 `now()-7201` 再申请，断言被拒；重复确认后 `completed` 时间戳不变（幂等）；批准撤回后被撤销的那次确认清零，但原时间写入 `confirmation_history`。

#### 3.2.6 通知队列 `db.notify` / `db.deliver_notices`

- **为什么单测**：通知是"写入队列表、打开收件箱时投递"的两段式，历史上出现过"通知失败导致下单回滚"（Q05）。
- **怎么测**：入队后 `notice_queue` 有 1 条、`notices` 为 0；投递后互换且只投给本人；再投递一次不重复；用 `CREATE TRIGGER ... RAISE(ABORT)` 注入失败后，队列保留、`notices` 仍为 0，解除故障后重投成功。

## 6 测试发现

### 6.1 失败的用例

**无。** 105 项用例两轮全部通过，没有出现阻断交付的缺陷。

需要说明的是：本轮的角色是"补测试"，产品代码一行未改；新增用例时出现的报错都来自用例自身写错，下面是修正记录，避免以后误认为是产品缺陷。

### 6.2 编写用例时修正的问题（均属用例自身）

| 现象 | 原因 | 修正 |
| --- | --- | --- |
| 撤回通知断言取到"有新订单，请接单或拒绝" | 卖家队列里已有多条通知，`SELECT ... WHERE user_id=?` 取到最早一条 | 增加 `last_notice()` 取 `ORDER BY id DESC LIMIT 1` |
| 审计断言查不到记录 | 用例直接调 `confirm_delivery()`，绕过了负责写审计的 `act()` | 审计类用例改为经 `act()` 调用 |
| "接收人不存在"分支永远测不到 | 先命中了"咨询必须关联商品卖家"，该分支不可达 | 改用卖家身份触发（`uid == seller` 时才继续查接收人） |
| `TestProductFields` 报 `AttributeError: raises` | 该类继承 `unittest.TestCase`，而 `raises()` 定义在数据库测试基类里 | 抽出 `UnitCase` 基类，两个基类都继承它 |

### 6.3 产品代码观察（不影响本次验收，建议后续处理）

以下 6 条都用脚本或单元用例核实过现象，属于"低风险改进项"，**不是**本轮测试失败项：

| 编号 | 位置 | 现象 | 复现 | 建议 |
| --- | --- | --- | --- | --- |
| OBS-01 | `services.review_product` / `freeze_product` / `unfreeze_product` | 先 `get()` 取对象再 `administrator()`，非管理员用不存在的 id 会得到"对象不存在"而不是"需要管理员权限"，可探测对象是否存在 | 买家调用 `review_product` + `id=9999` → "对象不存在" | 把 `administrator(user)` 提到 `get()` 之前（其余后台动作已是这个顺序） |
| OBS-02 | `services.handle_report` | 不校验举报当前状态，同一举报可重复处理，后一次结论覆盖前一次并再发一条通知 | 对同一 `id` 连续调用 `handle_report` → 第二次结论生效 | 增加 `need(obj['status'] == '待处理', '举报已处理')` |
| OBS-03 | `services.submit_review` | `int(payload.get('rating'))` 接受 JSON 布尔值，`true` 被当成 1 分 | 提交 `{"rating": true}` → 入库为 1 分 | 先判 `isinstance(rating, int) and not isinstance(rating, bool)` |
| OBS-04 | `services._product_fields` | 图片前缀与文件头分别独立判断，标称 PNG、内容为 JPEG 的 data URL 仍通过 | `data:image/png;base64,` + JPEG 字节 → 接受 | 让前缀与文件头一致后再判断（安全性不受影响，仅是提示口径） |
| OBS-05 | `db.deliver_notices` | 假定调用时没有活动事务：在事务内调用会在 `BEGIN IMMEDIATE` 抛 `OperationalError`（该行在 `try` 之外，不会回滚也不会被吞掉） | 在 `BEGIN IMMEDIATE` 之后调用 → `OperationalError: cannot start a transaction within a transaction` | 在函数注释写明"必须在无事务时调用"，或改用 `SAVEPOINT`；当前仅 `/api/mine` 在新建连接后立即调用，符合约定 |
| OBS-06 | `services.get` 及部分 `int()` 转换 | 非数字 id 抛 `ValueError` 而非 `BusinessError`，业务层异常类型不统一 | 已由 `test_rating_must_be_an_integer` 固定当前行为 | 统一包装为 `BusinessError`（接口层已把两者都映射为 400，用户可见行为正确） |

## 7 结论与建议

### 7.1 结论

1. **功能正确性**：105 项自动化用例（78 单元 + 27 集成）两轮全部通过，覆盖账号与 CSRF、发布审核检索、收藏咨询、并发下单、取消与确认、撤回与争议、冻结封禁、举报审计、统计导出、通知重试等主要链路。
2. **代码覆盖**：业务核心四层 317 条语句、34 个分支 100% 覆盖；接口层 97%；未覆盖部分是两个 500 兜底分支与两个命令行入口脚本。
3. **质量状态**：未发现阻断性缺陷；6 条低风险改进项已登记（OBS-01～OBS-06），其中 OBS-01（越权探测）与 OBS-02（重复处理举报）建议优先修。
4. **可重复性**：测试不依赖网络、不修改 `data/campus.db`，随机端口 + 临时库，同一机器上可稳定复跑。
